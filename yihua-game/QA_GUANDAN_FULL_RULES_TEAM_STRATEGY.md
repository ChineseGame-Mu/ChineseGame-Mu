# Clean-room 掼蛋完整规则与团队策略 QA 标准

本文件是 `cleanroom/yihua-game-20260826` 的机器人 QA **硬性验收标准**。仅完成若干局、无死锁，不再等同于 QA 通过。

## 1. 总目标

机器人必须按接近人类自然打牌的方式完成完整掼蛋赛程：从级牌 2 开始，依规则升级，持续打到 A，并在通过 A 后产生最终获胜队伍。测试既验证规则正确性，也验证真实出牌、队友配合、升级逻辑和统计报告。

## 2. 全规则覆盖（硬门槛）

QA 必须覆盖当前游戏规则引擎支持的全部掼蛋规则，并至少实际验证以下出牌类型：

- 单张
- 对子
- 三张
- 三带二 / 当前规则引擎支持的三张组合
- 顺子
- 连对 / 木板（若当前规则引擎支持）
- 钢板 / 连续三张（若当前规则引擎支持）
- 同花顺
- 普通炸弹（至少 4、5、6 张；规则支持更大炸弹时继续覆盖）
- 王炸 / 当前规则定义的最高炸弹
- 级牌、逢人配等特殊牌规则（若当前规则引擎支持）
- 首出、跟牌、压牌、过牌、重新取得出牌权
- 一方/一人出完后的接风、剩余玩家顺序、末游自动归位
- 双下、头游/二游/三游/末游以及相应升级计算
- 从 2 到 A 的升级、A 级胜负与通过 A 后的整场结束条件

如果某个牌型因随机发牌在单次赛程中没有自然出现，QA 必须用确定性牌局/种子补充覆盖；不得因为“这一局没有发到”而跳过。

## 3. 人类自然出牌策略（硬门槛）

机器人不得只会找一张最小可压牌。策略至少满足：

1. **从小到大、先清杂牌**：在不破坏关键组合、不浪费控制牌的前提下，优先清理较小、较孤立的牌。
2. **保持牌型结构**：能用对子、三张、顺子、连对等自然牌型出牌时，不应无意义拆散成单张。
3. **炸弹节制**：普通情况下保留炸弹；只在夺回关键出牌权、阻止对手冲刺、保护队友胜势或自己/队友即将出完时使用。
4. **控制牌管理**：大王、小王、级牌、大炸弹等高价值控制资源应服务于整队获胜，不应机械地见大就出。
5. **残局意识**：根据自己、队友和对手剩余牌数改变策略；有人接近出完时提高拦截或护送优先级。

## 4. 队友配合策略（核心硬门槛）

每轮发牌后，分别对同队队员计算“牌面强度/出完潜力”，选出本轮本队的 **主攻队员（best-hand / captain）**。策略目标是：优先帮助本队主攻队员尽快成为头游，同时保证团队总体升级收益最大。

必须实现并记录下列协作行为中的实际发生项：

- **让牌**：队友已经掌握当前牌权且继续出牌有利时，不无意义压队友。
- **送牌/喂牌**：取得牌权后，优先领出主攻队员更容易接走的牌型或点数。
- **护送**：主攻队员剩牌少时，使用控制牌或炸弹阻断对手，帮助主攻队员再次取得牌权。
- **接风配合**：队友出完后的接风机会优先转化为本队继续掌控节奏。
- **拆牌支援**：必要时允许辅助队员牺牲自己的漂亮牌型/控制牌，为主攻队员创造快速出完机会。
- **阻击对手**：对手即将出完时，即使需要提高出牌成本，也应优先阻止对手获得头游。
- **避免内耗**：除非为了防止对手夺权或有明确战术收益，不得用炸弹/大牌压同队队友。

主攻队员不是永久固定：当牌局变化后，若另一名队友明显更接近出完，策略可动态切换主攻对象，但必须在报告中记录切换原因。

## 5. 完整赛程验收（硬门槛）

- 起始级别：2。
- QA 必须持续进行真实完整牌局，而不是固定只测 3 局。
- 至少一支队伍必须依当前游戏正式升级规则一路推进到 A，并在 A 级完成正式获胜条件。
- 若达到动作/时间上限但无人完成“通过 A”，QA 结果必须为 fail / incomplete，不得判 success。
- 全程不得出现 deadlock、state error、crash、非法出牌被接受、合法出牌被错误拒绝、错误轮次/错误接风/错误升级。

## 6. 牌型覆盖门槛

最终报告必须包含 `playTypeCoverage`。以下核心项计数必须 > 0：

`single`, `pair`, `triple`, `straight`, `straightFlush`, `bomb4`, `bomb5`, `bomb6Plus`。

当前规则引擎支持的其它正式牌型也必须出现在规则单元/确定性场景覆盖表中。不能自然随机覆盖的项目必须通过 deterministic scenario 证明。

## 7. 每队统计分析报告（硬门槛）

QA 必须同时输出机器可读 JSON 和人可读 Markdown 报告。每支队伍至少包含：

- 队伍名称
- 参赛队员姓名/机器人名
- 每轮开始等级、结束等级、升级结果
- 每轮四名/全部参赛者名次（按当前桌型）
- 本轮主攻队员及其牌面强度摘要
- 本轮实际使用的牌型及次数
- 本轮关键炸弹/同花顺使用时机
- 本轮使用了哪些队友配合方式
- 每次关键配合的简短说明：谁帮助谁、使用何种方式、结果是什么
- 是否发生主攻队员切换及原因
- 本轮获胜/升级的主要原因摘要
- 累计胜局、头游次数、升级级数、从 2 到 A 所用轮数

建议 JSON 关键字段：

```json
{
  "qaStandard": "guandan-full-rules-team-strategy-v1",
  "completedThroughA": true,
  "winnerTeam": "Team A",
  "playTypeCoverage": {},
  "deterministicRuleCoverage": {},
  "teams": [
    {
      "teamName": "Team A",
      "players": [],
      "rounds": [
        {
          "round": 1,
          "levelBefore": "2",
          "levelAfter": "3",
          "captain": "Bot-1",
          "coordinationMethods": ["让牌", "送牌", "护送"],
          "keyCoordinationEvents": [],
          "winReason": ""
        }
      ]
    }
  ]
}
```

## 8. QA success 判定

只有同时满足以下条件才允许 `success`：

1. 全部规则测试/确定性覆盖通过；
2. 核心牌型覆盖计数满足门槛；
3. 人类自然出牌策略检查通过；
4. 队友配合检查通过，且报告存在真实协作事件；
5. 至少一队从 2 打到 A 并通过 A 获得最终胜利；
6. 每队 JSON + Markdown 统计分析报告完整生成；
7. deadlocks = 0、stateErrors = 0、crashes = 0；
8. 没有非法状态、非法升级、非法出牌或错误接风。

任何一项缺失都必须判定 QA 失败，不得用“完成三局”替代完整验收。
